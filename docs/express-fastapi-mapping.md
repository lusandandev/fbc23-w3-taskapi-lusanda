# Week 2 Express → Week 3 FastAPI mapping

| Concept | Week 2: Express / TypeScript | Week 3: FastAPI / Python | What changed or stayed the same |
|---|---|---|---|
| **Entry point** | `api/src/server.ts`. The `startServer()` function loads configuration, opens SQLite, creates the schema, seeds demo users in development, wires dependencies, creates the Express app, and calls `app.listen()`. `npm run dev` starts this file through `ts-node` and Nodemon. | The Docker command runs `alembic upgrade head` and then `uvicorn app.main:app`. Uvicorn imports the `app` object from `app/main.py`. | Both have a clear process entry point. Week 2 starts the Node/Express process directly; Week 3 starts the container command, applies migrations, and then starts the ASGI server. |
| **Startup sequence** | `server.ts` calls `loadConfig()`, `openDatabase(config)`, `createSchema(db)`, optionally `seedDemoUsers(db)`, constructs repositories/services/controllers, calls `createApp(...)`, and listens on the configured port. | Docker Compose starts PostgreSQL and waits for its health check. The API container applies Alembic migrations before Uvicorn starts. `app/main.py` creates the FastAPI instance, includes routers, and registers middleware and exception handlers. Database sessions are created when request dependencies are resolved. | Week 2 creates/checks its SQLite schema at application startup. Week 3 uses versioned migrations against PostgreSQL before serving requests. |
| **Middleware and request pipeline** | `api/src/app.ts` registers middleware in order: `cors(...)`, then `express.json({ limit: '10kb' })`. It registers `/health`, mounts the login routes, mounts task routes behind `createRequireAuth(...)`, then registers the not-found response and `errorHandler`. The auth middleware is mounted specifically on `/tasks`. | `app/main.py` registers `@app.middleware("http")` to log method, path, status and duration. Authentication is declared as a route dependency with `Depends(get_current_user_id)`, rather than as a global HTTP middleware. FastAPI exception handlers handle validation and unexpected errors. | Both use a request pipeline around route handling. Week 2 uses ordered Express middleware for CORS, JSON parsing and task authentication. Week 3 uses HTTP middleware for request logging and FastAPI dependencies for per-route authentication and resources. |
| **Routing** | `createAuthRoutes()` in `api/src/routes/auth.routes.ts` maps `POST /login`. `createTaskRoutes()` in `api/src/routes/task.routes.ts` maps `GET /`, `POST /`, `PATCH /:id`, and `DELETE /:id`; `app.ts` mounts that router at `/tasks`. | `APIRouter` groups endpoints in `app/routes/`. Decorators such as `@router.post`, `@router.get`, `@router.patch`, and `@router.delete` bind methods and paths. The task router has the `/tasks` prefix; auth has `/auth`; health has `/health`. | Express uses `Router()` and `router.get/post/...`; FastAPI uses `APIRouter` and decorators. Week 3's contract is broader: it adds registration and `GET /tasks/{task_id}`. Week 2 has login at `/login`, while Week 3 uses `/auth/login`. |
| **Request validation** | Zod schemas live in `api/src/schemas/`. Controllers call `parseOrThrow(schema, input)` from `api/src/errors.ts`; that helper runs `safeParse()` and converts Zod issues into an `AppError` with field errors. Validation therefore happens at the controller boundary, not in a separate validation middleware. | Pydantic models in `app/schemas/` define validated request bodies and response shapes. FastAPI reads model, path and query parameters from route signatures and validates them before calling the route function. `RequestValidationError` is handled in `app/main.py` and returned as HTTP 400 to match the brief. | Both validate untrusted input before business logic. Week 2 explicitly invokes Zod from controllers; Week 3 declares Pydantic models and lets FastAPI perform validation from route parameters. |
| **Dependency injection** | Dependencies are constructed manually in `api/src/server.ts`: database-backed repositories, `JwtService`, services and controllers are instantiated and passed into `createApp(...)`. `AuthService` receives a `UserRepository` and `JwtService`; `TaskService` receives a `TaskRepository`. `createApp` receives its `AppDependencies` object. | FastAPI's `Depends` declares dependencies in route signatures and provider functions. `get_db()` yields a SQLAlchemy session; `get_task_controller()` uses that session to build `TaskRepository → TaskService → TaskController`; `get_current_user_id()` validates the bearer token and provides the user ID. The auth router has a corresponding `get_auth_service()` provider. | The principle is the same: collaborators are supplied rather than created inside the business logic that uses them. Week 2 wires the object graph once in the composition root. Week 3 declares provider functions and lets FastAPI resolve them for each request. |
| **Configuration** | `api/src/config.ts` optionally loads `api/.env` using `process.loadEnvFile()`, validates `process.env` with a Zod `EnvironmentSchema`, and returns a typed `AppConfig`. `NODE_ENV`, `PORT`, `WEB_ORIGIN` and `DATABASE_PATH` have defaults; `JWT_SECRET` is required. | Docker Compose reads `.env` for interpolation and passes required values into the API and database containers. `app/config.py` reads environment variables, validates required values (including PostgreSQL URL format, JWT secret length and token lifetime), and caches the immutable `Settings` object with `lru_cache`. | Both keep environment-specific values outside application logic and validate configuration before use. Week 2 validates Node environment variables with Zod; Week 3 validates container-provided environment variables in Python. |
| **Error handling** | `AppError` in `api/src/errors.ts` carries an HTTP status and optional field errors. `parseOrThrow()` converts Zod failures to `AppError`. The auth middleware forwards errors with `next(error)`. `api/src/middleware/error-handler.ts`, registered last in `app.ts`, formats known errors, handles malformed JSON (400) and oversized bodies (413), and logs unexpected errors before returning a safe 500. `app.ts` returns a JSON 404 for unmatched routes. | Controllers translate expected service errors into `HTTPException` responses (for example, 404 for missing/other-user tasks and 409 for the forbidden `done → todo` transition). `app/main.py` converts `RequestValidationError` into 400 and logs unexpected exceptions while returning a generic 500. The health route logs database-check failures and returns 503. | Both separate expected client/domain errors from unexpected server faults and avoid exposing internal exception details. Week 2 funnels errors through Express error middleware; Week 3 uses FastAPI's `HTTPException` and registered exception handlers. |
| **Database access** | `api/src/db/connection.ts` opens SQLite through `sqlite`/`sqlite3`; `createSchema()` creates/checks tables. SQL is in `SqliteTaskRepository` and `SqliteUserRepository`, which implement repository interfaces in `api/src/repositories/interfaces.ts`. | PostgreSQL is accessed through SQLAlchemy sessions from `app/db/session.py`. ORM models are in `app/models/`; repository classes in `app/repositories/` own SQLAlchemy queries and persistence. Alembic migrations define and apply schema changes. | Both keep persistence behind repositories so services do not contain SQL. The database and schema lifecycle changed: Week 2 uses SQLite and schema creation at startup; Week 3 uses PostgreSQL and versioned Alembic migrations. |

## How dependency injection works in each project

### Week 2: manual constructor injection

1. `server.ts` opens the SQLite database.
2. It constructs `SqliteUserRepository(db)` and `SqliteTaskRepository(db)`.
3. It constructs `JwtService`, then `AuthService(userRepository, jwtService)` and `TaskService(taskRepository)`.
4. It constructs `AuthController(authService)` and `TaskController(taskService)`.
5. It passes the controllers and JWT service into `createApp({ ... })`.

The services receive their dependencies through constructor arguments. The composition root (`server.ts`) is responsible for knowing which concrete repository implementations to use.
